# QQ 通道的权限档位与群聊取舍

私聊会话在建完 agent 后**显式**写入 `workspace-write` 沙箱与 `never` 审批策略（不继承 profile 默认，也不挂 `ctx.permissionPresets`），不注册 `approval/request` 应答者；群 @ 不建会话，只回一句「私聊我」。

两个反直觉的取舍，值得记下来：

**群聊不接，是因为沙箱只挡写不挡读。** `dsh-fs-sandbox` 的约定是「限制模型对文件的写入与编辑，同时保留本地文件系统的读取行为」，bash 的 `read-only` 同样只是可写根为空。所以「群聊降级成 `read-only`」不是安全边界——群里任何人 @ 一下，都能让 agent 读整台机器上的文件（`~/.ssh`、`.env`、别的仓库）并念回群里。v1 没有可用的隔离层（真正的隔离要给群聊裁剪工具集），因此群聊整体不接。私聊不同：那是单人对自己的 agent 说话，读权限不构成越权。

**审批不接，是因为收益低于成本。** 请求只带 `toolName` / `callId` / `reason`，**没有命令原文**，要让用户看清「到底要跑什么」得拿 `callId` 回会话日志捞参数——捞出来也未必完整。答复又只能靠纯文本（按钮回调要额外的 `INTERACTION` intent，配错即断连），而那条「1」会跟「新消息 = 新一轮」抢同一个入口。与此同时，审批只在工具撞到沙箱边界、想带 `sandbox_permissions` 升权重试时才触发，不是每次工具调用——不接的代价只是「出界操作失败」，而不是「工具跑不了」。`never` 还会告诉模型本会话不允许升权，避免它反复重试。

## Consequences

- 出界操作（碰 `~/.dsh/qqbot-workspace` 之外）在 QQ 里永远失败，用户必须去 Web UI 才做得成。这是有意的：失败是显式的、可解释的，比一个盲批的入口好。
- `intents` 仍是 `1<<25`，群 @ 和私聊共用这一位、过滤不掉。即使群聊不建会话，网关照样会推 `GROUP_AT_MESSAGE_CREATE`，插件必须显式忽略或兜底回话，不能让它漏进会话创建路径。
- 想放开任何一档（群聊接入、或私聊升到 `danger-full-access`），都要先有一层真正的读隔离或可信的身份边界，那是另一个 effort，不是改一个配置值。
